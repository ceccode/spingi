# 0029: `spingi.api` is the public Python surface; the command line and the MCP server are skins over it

Status: Accepted · Date: 2026-11-24 · Milestone: A1

## Context
Spingi had one way in, the command line, and `cli.py` did the wiring itself: it built the session, chose the operator, mapped `--realistic` onto four settings, printed. A program that wanted to run a plan had to import `SessionConfig`, `run_session`, `ScriptedHuman` and `EventLog` and repeat that wiring, with no word on which of those names would still be there in the next version. Reading what happened meant parsing `events.jsonl` by hand. An MCP server is about to be a second way in (ADR-0030); written straight on the internals it would have been a third copy of the wiring, and the three would have drifted apart: a check that says one thing on the command line and another to an agent.

## Decision
- **One module is the interface.** `spingi.api` holds what a program needs: `robots`, `skills`, `plan_schema`, `scene_schema`; `scenes`, `plans`, `read_scene`, `read_plan`; `describe_scene`, `check_scene`, `scene_map`, `save_scene`; `parse_plan`, `check_plan`; `run` and `bench` with their async forms `arun` and `abench`; `episodes`, `episode_summary`, `events`, `frame`. This module, the episode format and the YAML of plans and scenes are the stable interface. The rest of the package is internal and may change between versions.
- **Things are named as on the command line.** A scene or a plan is a file, a file of the working folder's `scenes/` or `plans/`, or a sample's name (ADR-0027); `root` is that working folder. A plan may also be a `TaskPlan`, a mapping, or text through `parse_plan`; given as data, it is written under the runs folder, named by its id and its content, so that the episode keeps its copy.
- **Results are data.** Every function returns pydantic models: a `RunReport` with an `EpisodeSummary`, each step with its attempts, outcome and reason, the console's lines as a timeline, the run's metrics, the frames the robot analysed and how to open the run in the viewer. Nothing is printed: an MCP server's standard output is its protocol.
- **How close to the robot a run is has one name.** `mode` is `fake`, `kinematic`, `physics` or `realistic`; `session.MODES` says what each means as session settings, and `--realistic` on the command line is that entry.
- **The same checks, the same words.** `check_plan` makes the executor's own call to `validate_plan`, so it says what a run would say, and adds the scene's warnings (ADR-0028). What cannot start raises before a run folder is made: `PlanError`, `SceneError`, `UnknownSample`, `ValueError` for settings that contradict each other.
- **No stop button without a terminal.** `run_session` installs the Ctrl+C handler only when asked; the API does not ask. A program cancels the task: the robot is stopped, the run ends as aborted and the episode is still written.
- **Frames are fetched by reference, inside the episode.** An episode may come from a stranger: `frame` returns only an image in the episode's own `frames/` folder, with symbolic links resolved.
- **The skins stay thin.** `spingi skills`, `robots`, `scenes`, `plans`, `check` and `map` call the API. `run` and `bench` keep their own wiring, because they add what a library has no use for: the operator console, live event lines, the stop button. A test forbids `spingi.api` to import the command line or the MCP server, and anything in the package to import the command line.

## Consequences
- **Three lines run a plan**: `from spingi import api`, `report = api.run("yard_patrol", "yard_outdoor", robot="go2", mode="physics")`, `report.summary.timeline`.
- **A promise to keep.** A name in `api.__all__`, or a field of a model it returns, changes only with a version that says so; additions are free. Internal modules can be reorganised without telling anyone.
- **A request for a person is answered by a fixed policy.** `on_failure` (`abort`, `skip` or `retry`) is the answer to every operator request in an API run, as with `--operator auto`. Supervising a run stays the console's job.
- **Small moves inside.** `parse_plan` next to `load_plan`, with YAML mistakes as a one-line `PlanError`; the world's description for the planner from `planner/llm.py` to `scenes.py`; a skill's one-line summary to `spingi.skills`; the console's line for an event as a function. No behaviour changes on the command line except one: `spingi plans --show` of an unknown name says what a name may be.
- **35 new tests**: the API used by name with plain data back, the executor's messages from `check_plan`, a plan given as data, a failing step with its attempts and the fixed answer, what cannot start raising before a run folder exists, events reaching the caller, the modes on the simulator, a cancelled run, frames confined to the episode, and the two import rules.
