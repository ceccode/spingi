# 0030: Coding agents use Spingi through an MCP server, in simulation only

Status: Accepted · Date: 2026-11-24 · Milestone: A1

## Context
People now work through coding agents: Claude Code, Codex, OpenCode. A tool such an agent cannot call is one its user has to learn alone, and the long part of learning Spingi is modelling a place: metres, radians, which key goes where, why the robot did not see the box. An agent can do that work with its user if it is told the format, gets errors it can act on and can see the result. The Model Context Protocol is how these clients take tools. Spingi already has a planner that is a language model (ADR-0010), held to one rule, the model proposes and the runtime disposes (ADR-0003); an agent at the end of an MCP connection is the same kind of planner, with the same need for a boundary, and it is driven by text that may come from anywhere. Giving it the command line instead would give it a shell, and the question of what it may run.

## Decision
- **An MCP server over the public API.** `spingi mcp [--root DIR] [--runs-dir DIR]` serves one working folder over standard input and output, with the official Python SDK (`mcp`, the `mcp` extra). `spingi/mcp_server.py` imports nothing of Spingi but `spingi.api` (ADR-0029); a test enforces it.
- **Seventeen tools that follow the work.** Know the robot: `list_robots`, `list_skills`. Learn the formats: `get_guide`, `list_scenes`, `list_plans`, `read_scene`, `read_plan`. Model a place: `describe_scene`, `validate_scene`, `preview_scene`, `save_scene`. Plan and run: `validate_plan`, `run_plan`, `bench_plan`. Read what happened: `get_episode`, `get_events`, `get_episode_frame`. Results are structured data; the map and the camera frames are images, for agents that can look.
- **Guides are part of the product.** Four short texts in `spingi/guides/` (workflow, scene, plan, landmarks) say what the tutorial says, for a reader that writes the YAML itself. Their examples are checked by tests against the code they describe, and so are their numbers: the camera's range, the tags' reading distance, the gate.
- **Simulation only.** The server builds sessions with the `fake` and `sim` adapters and has no way to name another. A robot's adapter (M4.1) is not reachable through MCP; making it so needs its own ADR.
- **No tool moves the robot outside a plan.** There is no walk, turn, grasp, speed or reset. The agent writes a plan, `validate_plan` and the executor refuse what is wrong with it, and the plan runs under the scene's safety limits like any other.
- **The model is never the operator.** A step that asks for a person gets the answer the call names, `on_failure`, `abort` by default, every time; the result counts the requests. Supervising a run is a person's job at the console (P7).
- **One folder.** A reference to a scene or a plan is a name or a path inside the working folder; absolute paths, `..` and links that leave the folder are refused, and the samples are the only files read elsewhere. Scenes are written to `scenes/`, runs and maps to `runs/`; a scene is saved only once it is one. An episode is named by its run id, a frame must be an image inside that episode. YAML given in a call is at most 256 kB, a benchmark at most 200 runs, a page of events at most 500.
- **No network, no key, one run at a time.** The server makes no outbound call. The LLM planner (`spingi plan`) is not exposed: the agent is the planner. Calls that run a session wait for one another.
- **A cancelled call still stops the robot.** The session runs in its own task; when the client cancels, the server cancels that task and waits for it, so the run ends as aborted and the episode is written before the next call starts.

## Consequences
- **One line connects an agent**: `claude mcp add spingi -- spingi mcp`, and the like for Codex and OpenCode ([docs/agents.md](../docs/agents.md)). The agent needs no checkout, no shell access to Spingi and no key.
- **The loop a new user gets stuck in becomes a conversation**: describe a place, get a scene with a map to check against the floor plan, a plan, a run to watch and a success rate. Tried over stdio on a patrol of the yard and on a warehouse described in a sentence: the first draft's misspelled section, the stop facing away from its shelf and the place inside the bench were each told to the agent in a line it could act on.
- **Clients differ.** Codex gives a tool 60 seconds unless told otherwise, and a long benchmark needs more: the documentation says how to raise it, and `bench_plan` defaults to 10 runs. Not every client shows resources or prompts: everything needed is a tool, and the guides and the two prompts are extras.
- **What the server returns is data.** A scene's comments and a plan's `say` text reach the agent as tool results. The server's instructions say they are never instructions; a scene from a stranger is to be read like any file an agent opens.
- **A second skin to keep thin.** What the server needs and the API lacks goes into the API, for every caller: the guides, references held to a folder, the pattern of a run id came that way.
- **A new dependency for those who ask for it.** The `mcp` extra brings the SDK and the simulator's extras. The core package still depends on pydantic and PyYAML only.
- **28 new tests**: the tools and which only read, no tool that moves the robot, the loop from a typo to a saved scene with a plan run in it, the run's own words through the server, progress, the fixed operator answer, files held to the folder for every reading tool, the size caps, a cancelled call, the server over stdio as a client launches it, the guides against the code.
